# The vanilla ceiling for this case, measured on the card that ran it

Machine: 2x RTX 4090 (24564 MiB each, 23.52 GiB usable to cupy), CUDA 13,
`ssh -p 27434 root@91.203.49.76`, GPU 0, card otherwise empty.
Configuration: `configs/superoutbreak_20110427_d01_960.toml` --
960 x 960 x 49 at dx = 3 km, dt = 15 s, Morrison mp10 + MYNN (bl_pbl 5) +
Noah-MP (sf_surface 4) + RTE-RRTMGP (ra_lw/ra_sw 4), no cumulus scheme
(convection-allowing), real Lambert, real terrain, specified lateral
boundaries from ERA5 every 3 h.

## What ran and what refused, 2026-08-09, run started 14:48:26Z

    statics built in 88.5 s
    30 row slabs of <= 32 rows (+1 halo row)
    forcing 2011-04-27 15:00:00: 30 slabs, perimeter kept; pool 9.68 GiB
    forcing 2011-04-27 18:00:00: 30 slabs, perimeter kept; pool 9.68 GiB
    ... (5 forcing times)
    prepared 960x960x49 from 5 forcing times in 773.4 s
    ingest device high-water 15.55 GiB (18116 B per mass cell)

So `realcase.prepare_slabbed` -- the row-slab ingest -- FITS: 15.55 GiB of a
23.52 GiB card. The production in-order ingest does not: it was measured at
35.9 kB per mass cell, which is 30.8 GiB at this domain.

The next thing a streamed run does is `build_stores`, and its first act was
ONE monolithic `dycore.step` over the whole domain, to settle carriers that
some physics rungs allocate lazily. That step is a RESIDENT full-domain step
-- exactly the operation this domain is too big for -- and it refused:

    File ".../tilestream/realcase.py", line 1004, in build_stores
      _step(state, cfg)
    File ".../gpuwm/core/dycore.py", line 2307, in step
      physics_tendencies = state.physics.compute(state, cfg)
    File ".../gpuwm/core/physics.py", line 3409, in compute
      self._run_radiation(atmosphere, state, cfg)
    File ".../gpuwm/core/rrtmgp.py", line 2065, in __call__
      paths = hydrometeor_paths(...)
    File ".../gpuwm/core/rrtmgp.py", line 1211, in hydrometeor_paths
      re_s = exponential_radius(qs, nsp, 100.0)
    cupy.cuda.memory.OutOfMemoryError: Out of memory allocating
      180,633,600 bytes (allocated so far: 24,429,406,208 bytes).

180,633,600 B is one 960 x 960 x 49 float32 field. The refusal is inside
RRTMGP, on the first radiation call, which is the cadence boundary the
milestone notes warn about: a domain that "allocates" is not a domain that
runs, because the schemes that allocate the most scratch fire on their own
cadence and not on step one.

**This is the ceiling.** Vanilla -- a resident `DomainState` stepped whole --
cannot integrate 960 x 960 x 49 at this physics rung on a 24 GiB RTX 4090.
An independent measurement on a 32 GiB RTX 5090 (branch `tilestream-case2011`,
commit 5383fbe) refused the same configuration the same way, after 29.53 GiB.

## What the streamed run does instead

`build_stores(settle=False)` skips that step. It is not skipped on faith:

* `tilestream.settle_check` at 192 x 192 x 49 on this case's own config
  reports `identical: true` -- 214 carriers before, 214 after; geography
  unchanged; the wrfout frame plan 123 fields before and after. At this rung
  (no cumulus scheme) nothing is allocated lazily.
* `driver.run_tiled` compares each tile buffer's carrier inventory with the
  store's and raises `TiledRunError` naming the difference BEFORE it steps
  anything, and the tile buffers themselves warm up. A rung that really did
  allocate a carrier lazily would be refused loudly at the first sweep, not
  silently short a field.
